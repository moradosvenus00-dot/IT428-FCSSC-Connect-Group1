## Development and review workflow

1. Work on the suggested feature branch, or record the actual branch used. Keep changes focused on assigned pages and coordinate shared-file edits.
2. Commit your work under your own GitHub identity. Record the exact commit link in your member file.
3. Open a pull request to `main`; link it in your member file. A PR is not marked merged until GitHub shows that status.
4. Run relevant checks and record the command or feature tested, expected and actual results, pass/fail outcome, and verification date.
5. Have a teammate review integration points before merge. Record review and merge evidence separately from implementation.

## Individual technical verification

Each member should be ready to locate and explain their code, describe the React props/state and event handling they used, demonstrate the assigned feature, and make a small live change. Show the relevant commit or PR, along with a test record. For shared files, document the exact lines or behavior you changed rather than claiming exclusive ownership of the file.

## Keeping records current

After finishing a task, update the assigned-responsibility checklist, source table, progress checkboxes, testing record, and issues in your own document. Use real commit and PR URLs. If work exists only in a local working tree, label it **uncommitted** and keep authorship or review marked **unverified** until there is evidence. Do not replace a prior failed test with a pass without recording the new run and date.
